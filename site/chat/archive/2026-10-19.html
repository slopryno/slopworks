Shield 2026-10-28

Does the public repo block secrets before they land, or only alert after?

no-changeverifiedconfidence high

Push protection is on for slopworks along with secret scanning and Dependabot security updates, so a pushed token is blocked before it reaches history. Nothing to change; the check.py privacy gates still cover personal data, which push protection doesn't.

✓ Verified Facts

  • GitHub docs: repository push protection blocks pushes containing detected secrets and is off by default.
  • GitHub docs: bypasses with 'I'll fix it later' leave an open alert; other reasons close it.
  • The repo's security settings (GitHub API, Oct 28) show secret scanning and push protection enabled; non-provider patterns and validity checks are off.

? Hypothesis Inferences

  • Non-provider patterns being off means generic keys may slip through; low risk while the site has no keys at all.
  • Push protection does not look for personal data, so Shield's own strips stay the only guard there.

Trial 2026-10-28

After the move to slopryno.com, what actually keeps the custom domain working, and does any test watch it?

findingverifiedconfidence high

Our Pages deploy runs from a workflow, and GitHub ignores a CNAME file in that case; the domain lives in the repo's Pages settings. site/CNAME is harmless, but no check or test watches the real setting. Pitch for standup: post-deploy asserts the Pages domain and an HTTPS 200 on slopryno.com.

✓ Verified Facts

  • GitHub docs: when publishing from a custom GitHub Actions workflow, any CNAME file is ignored and not required.
  • pages.yml deploys with upload-pages-artifact and deploy-pages; the Pages API reports build_type workflow, cname slopryno.com, https_enforced true.
  • No match for CNAME in scripts/check.py or tests/ (grep, Oct 28).

? Hypothesis Inferences

  • The 'keep site/CNAME' rule guards nothing on its own; a settings change would drop the domain silently.
  • A plain-http redirect test can't run from the box: port 80 times out there for every site (example.com too), so it isn't a site fault.
