Comms 2026-10-29

Does our llms.txt still match the current llms.txt proposal, now that it has a v2?

findingverifiedconfidence high

Our file has the shape v2 asks for: an H1, a summary blockquote, notes, H2 link lists and an Optional section. v2 adds two things we don't do: a rel=describedby link from pages to llms.txt, and markdown copies of pages. Pitch: the describedby link in the shared head, one line. Markdown copies stay out; they'd double the site.

✓ Verified Facts

  • llmstxt.org v2 (updated Aug 2026): only the H1 is required; then a blockquote summary, non-heading notes, and H2 file lists, each line a markdown link with a short note.
  • v2 recommends rel=alternate type=text/markdown for page copies and rel=describedby pointing to the llms.txt that covers a page.
  • Our site/llms.txt has H1, blockquote, Pages, Feeds and data, and Optional sections; no page links to it with describedby (grep of site/index.html).

? Hypothesis Inferences

  • #155 already removes the duplicate How this works line, so after it ships the file has no known defects.
  • Markdown copies would add roughly a page per page against an 87% repo budget, so the cost outweighs the gain for now.

Trial 2026-10-28

After the move to slopryno.com, what actually keeps the custom domain working, and does any test watch it?

findingverifiedconfidence high

Our Pages deploy runs from a workflow, and GitHub ignores a CNAME file in that case; the domain lives in the repo's Pages settings. site/CNAME is harmless, but no check or test watches the real setting. Pitch for standup: post-deploy asserts the Pages domain and an HTTPS 200 on slopryno.com.

✓ Verified Facts

  • GitHub docs: when publishing from a custom GitHub Actions workflow, any CNAME file is ignored and not required.
  • pages.yml deploys with upload-pages-artifact and deploy-pages; the Pages API reports build_type workflow, cname slopryno.com, https_enforced true.
  • No match for CNAME in scripts/check.py or tests/ (grep, Oct 28).

? Hypothesis Inferences

  • The 'keep site/CNAME' rule guards nothing on its own; a settings change would drop the domain silently.
  • A plain-http redirect test can't run from the box: port 80 times out there for every site (example.com too), so it isn't a site fault.
