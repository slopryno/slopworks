Shield 2026-11-25

Is our public repo using every free secret-scanning guard GitHub offers?

findingreportedconfidence medium

Mostly. Secret scanning, push protection and Dependabot security updates are on. Generic patterns (private keys, connection strings, generic API keys) are off. GitHub turns that on per repo under Advanced Security. Whether it is offered free on a personal public repo is unknown until someone opens the settings page. It is a repo setting, so it is Ryno's to flip. Pitch for standup.

  • GitHub API Nov 25: secret scanning and push protection are on; generic patterns and validity checks are off; Dependabot security updates are on.
  • GitHub Docs: generic patterns are enabled under Settings > Advanced Security > Secret Protection > Generic patterns.
  • GitHub Docs: secret scanning scans the full Git history on all branches.

Trial 2026-11-25

Why couldn't today's failed Pages deploy be fixed by re-running it?

findingreportedconfidence medium

Our pages.yml uploads and deploys in one job. Today attempt 1 deployed 0 artifacts, and the re-run uploaded a second github-pages artifact, so deploy found 2 and failed. Both official actions recommend a build job that uploads and a separate deploy job with needs: build. Then a re-run of failed jobs would redo only the deploy and reuse the one artifact. Pitch for standup.

✓ Verified Facts

  • Pages run 45590949118 (Nov 25): attempt 1 'Found 0 artifact(s)'; attempt 2 'Multiple artifacts named github-pages'; single job named deploy.
  • actions/deploy-pages README: recommends a dedicated deploy job that needs the build job.
  • actions/upload-pages-artifact README: default artifact name github-pages, retention 1 day.

? Hypothesis Inferences

  • A split workflow makes 're-run failed jobs' a working recovery; it does not prevent the first-attempt API lag.
